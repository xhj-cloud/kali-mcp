### 背景

对全部 **66 个 MCP 工具**做了实机全量测试（MCP 流式 HTTP 端点 `:8000/mcp`，共 68 次调用、多轮迭代），攻击类工具以最低强度对已授权靶机 `192.168.0.73` 实测。发现并修复 **8 处**代码问题，其中 `nmap_vuln_scan` 的超时问题经过三轮排查才定位到真正根因（详见下）。

测试环境：Kali 192.168.0.189/eth0（网关 192.168.0.1），靶机 192.168.0.73（VMware，开放 22/2222/8080-http-proxy）。

### 🐛 修复（8 处）

1. **`ping_host` 超时报 "bad linger time"**：`-W` 参数误传毫秒（`timeout*1000`），而 iputils 2025 版本 `-W` 单位是**秒**且严格校验（>4000 即报错）。改为直接传秒。
2. **`tcpdump_capture` duration 参数不生效**：时长只用于 executor 超时，未进入命令，导致"抓满 300s 被杀"报 `Failed (exit code: -1)`。改为命令内 `timeout -s INT {duration}`，并区分两种到点场景：有输出 → 成功 + "partial capture" 提示；零包 → 明确诊断 "No packets captured within the {duration}s duration — the interface was idle or the filter matched nothing."。
3. **`nmap_vuln_scan` 300s 预算被吃光**（三轮排查，前两轮是弯路）：
   - 弯路一：初判 `http-open-proxy` 是耗时主因，排除它之后仍超时；
   - 弯路二：尝试 `--script-exclude` → nmap 7.99 无此标志；再验证**空格双参形式** `--script "safe and not http-open-proxy"` 会静默不生效，必须用**等号形式** `--script=<表达式>`（此结论保留）；
   - **真正根因**：nmap 7.99 的 `safe`/`default`/`vuln` 分类内置了 **~40 个全网段 pre-scan 发现脚本**（`broadcast-*`/`targets-*`/`multicast-*`、`url-snarf` 30s 被动嗅探、`eap-info` EAP 握手等），对单主机扫描毫无意义，却独吞整个 300s 预算（`-d` 调试日志证实：373 个脚本加载，pre-scan 阶段 150s 仍未结束）；同时 `http-slowloris-check`（**vuln/safe 分类内的真实 DoS 脚本**）对不主动断连的代理目标会无限挂起。
   - **修复**：除 `all` 外所有分类统一排除 `broadcast-* targets-* multicast-* url-snarf eap-info mtrace mrinfo http-slowloris-check knx-gateway-discover`；移除此前对 `http-open-proxy` 的误判排除（实测它几秒完成，且对 8080 http-proxy 目标是有价值的检查）；`discovery` 分类从单主机工具中移除（语义不符，全网段发现请用 `nmap_scan`）；超时且有部分输出 → 成功 + 提示（原先报 Failed）。
   - **效果**（同一命令，靶机 22/8080）：`safe` 300s+ 超时 → **27.8s**；`vuln` 超时 → **124.8s**。
4. **`enum4linux_scan` 把"无结果"当失败**：目标无 SMB 服务时 enum4linux 退出码 1 但有正常输出。rc=1 且有输出 → 成功 + "exited 1 — no SMB/no results" 提示。
5. **`wpscan_scan` 两处**：(a) 目标非 WordPress 时退出码 4 / "does not seem to be running WordPress" 是正常结论，原报 Failed → 改成功 + 提示；(b) `enumerate` 参数加校验，非法 token（如 `vu`）给出明确错误并列出全部合法值（`p pt u vt vp ap cb dbe oc tb`），不再把错误原样丢给 wpscan。
6. **`sslstrip_run` 按计划停报 Failed**：到点（`timeout` rc=124）是设计行为，原报失败 → 改成功 + "stopped after the scheduled {duration}s duration (as designed)" 提示。
7. **`nuclei_results` 状态误报**：(a) 旧版"文件非空即完成"逻辑会把 11 天前的陈旧结果文件报成 "Complete"；(b) 扫描进行中也被误报。改为以 `\[INF\] Scan (?:finished|completed)` 作为完成标志（nuclei 输出按文件缓冲，该行只在进程退出时落盘，是唯一可靠信号），所有结果分支都附带结果文件 mtime（"Results file last updated: …"）便于判断新鲜度；进行中返回 "Scan In Progress" + mtime。
8. **`_fmt` 输出截断丢弃扫描发现**（第 5 轮测试发现）：8KB 上限只保留头部，而 nmap/nikto/ffuf 等扫描工具的**发现在输出尾部**（端口段在头、脚本结果和 `Nmap done` 在尾），原截断恰好把最重要的部分切掉。改 `_truncate` 为**头 40% + 尾 60%** 保留 + 明确省略标记（`... [N lines / M bytes truncated] ...`），总长仍受 8KB 约束。

### 🔍 排查过程中的重要发现（供参考）

- nmap 7.99 的 `--script` 表达式必须用等号形式；空格双参形式**静默**不生效（不报错）。
- 测试期间在 `url-snarf` 的被动嗅探输出里反复出现 `192.168.0.189 → 185.40.234.x/generate_204` 等公网代理探测 URL，一度误以为是 nmap 主动行为；实为局域网内某进程周期性校验公开代理列表（url-snarf 只是 `print(源IP, URL)` 被动记录），与本工具无关。
- iputils 2025 起 `ping -W` 单位改为秒且严格校验，旧文档/旧代码里的"毫秒"习惯会踩坑。
